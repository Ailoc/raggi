## 0. 结论摘要

本轮确认并修复了 **17 个问题**，其中 6 个属于“不会报错、只是结果悄悄不对/不安全”的类型：

| 级别 | 问题 | 影响 |
|---|---|---|
| 高 | URL 抓取只校验入口地址，重定向可进内网 | SSRF：可读云元数据、扫内网 |
| 高 | `stored_file()` 直读 Lance 旧表 | 默认 SQLite 部署下单篇删除漏删原文；重解析误报“无留档” |
| 高 | 删除文档先删文件、后删元数据 | 删除中途失败会留下“文档在、原文没了”且无法重解析 |
| 高 | 模型配置保存同步执行热切换/落盘 | 事件循环被阻塞（HuggingFace 可数秒），并发请求全部停住 |
| 高 | 健康/统计缓存无并发合流 | 32 个并发冷请求会同时做 32 次全表扫描（代码注释却写着“并发合流”） |
| 高 | 前端检索请求无取消/序号 | 慢的旧请求可覆盖新结果，参数与结果再次脱节 |
| 中高 | 请求体/列表参数无上界 | 构造请求可把内存、SQL 语句长度或循环推到不可控 |
| 中 | API key 过期时间损坏时放行 | fail-open：损坏的过期时间等价于永不过期 |
| 中 | 静态 token 用 `==` 比较 | 非常数时间比较（长期凭据） |
| 中 | 无 CSP/安全响应头 | 缺少纵深防御；API 响应也未禁缓存 |
| 中 | 模型 `timeout` 配置被忽略 | 用户改了配置但客户端仍用库默认超时 |
| 中 | Embedding 同 key 并发重复调 provider | 热门查询 cache stampede（16 并发 = 16 次远端） |
| 中 | SSE 流无终态时静默结束 | 半截答案被当成完整答案，或 loading 永远不结束 |
| 中 | 文档详情总带全部分块索引 | 大文档打开时响应体成倍膨胀（前端并未使用） |
| 低 | 设置页/原文检视存在旧响应覆盖 | 快速切换时显示上一次的对象 |
| 低 | 未鉴权且监听非回环地址无提示 | 容易被误部署成“同网段人人可写” |
| 低 | 构建新鲜度检查仍看 `.svelte/.css` | 迁移后守卫对真实源码失明 |

## 1. 安全

### 1.1 URL 抓取：重定向与 DNS rebinding（高）

**证据**：`load_url` 原来只对入口 URL 调 `_check_url`，随后用默认的
`urllib.request.urlopen`。urllib 会自动跟随重定向，而默认重定向处理器只校验
scheme，不校验主机。`public.example` 只要 302 到 `http://169.254.169.254/…`
即可绕过私网拦截。

**修复**（`rag/parsing/loaders.py`）：
- `_SafeRedirectHandler` 对**每一跳**重新执行 `_check_url`，最多 5 跳；
- 打开后对 `r.geturl()` 再校验一次最终地址；
- `_check_connected_peer()` 读取实际 socket 对端 IP 并复查——覆盖“解析时公网、
  connect 时内网”的 DNS rebinding 窗口；
- `_check_url` 同时拒绝 userinfo（`http://public@127.0.0.1`）、非法端口和超长 URL；
- 按响应声明的 charset 解码，不再一律按 UTF-8。

**测试**：`tests/test_security_hardening.py`（重定向到元数据地址、userinfo、非法端口、超长 URL）。

**残留**：没有把 DNS 解析结果钉到 socket（完整 pinning 需要自定义
`HTTPConnection`）；peer 复查已覆盖主要窗口，但仍有极窄的 TOCTOU 可能。
同时，本机 DNS 会把公网域名映射到 `198.18.0.0/15`，因此在本机 smoke 时
URL 入库会被正确拒绝——这是环境特性，不是回归。

### 1.2 API key 过期时间损坏时 fail-open（中）

`verify()` 对 `expires_at` 的 `ValueError` 原本 `pass`：数据损坏（手工改库、
迁移写脏）会让一把本应过期的长期凭据永久有效。现在改为抛
`ApiKeyAuthError("密钥过期时间无效…")`（`rag/storage/repos/keys.py:148`），
即**读不懂过期时间 = 拒绝使用**。测试：`test_malformed_expiry_fails_closed`。

### 1.3 静态 token 非常数时间比较（中）

`secret == legacy` 改成 `hmac.compare_digest`（`rag/api/auth.py:157`）。
静态 token 是长期凭据，不值得省这一步。同时把 CORS 预检的放行提前到任何查库之前，
预检不再为每次 `OPTIONS` 读一次密钥表。

### 1.4 CSP 与安全响应头（中）

新增统一安全头（`rag/api/__init__.py` 的 `SECURITY_HEADERS` /
`_finalize_response`）：

- `Content-Security-Policy`：`script-src 'self'`、`style-src 'self' 'unsafe-inline'`
  （MUI/Emotion 需要）、`frame-src 'self'`（PDF iframe）、`object-src 'none'`、
  `base-uri 'none'`、`frame-ancestors 'self'` 等；
- `X-Content-Type-Options: nosniff`、`X-Frame-Options: SAMEORIGIN`、
  `Referrer-Policy: no-referrer`、`Permissions-Policy`；
- API 响应统一 `Cache-Control: no-store`；静态 `assets/` 保持 immutable 强缓存。

为了能启用 `script-src 'self'`，`index.html` 里决定首帧主题的内联脚本外置为
`web/public/theme-boot.js`（Vite 原样复制到 `dist/`）。

**验证**：`test_csp_and_security_headers_on_api`、`test_index_has_no_inline_script`；
浏览器实测首页/文档页/PDF iframe 正常，控制台无 CSP 违规。

### 1.5 请求体与列表上界（中高）

- `_http_guards` 在鉴权/解析之前检查 `Content-Length`：文件上传按
  `max_upload_mb + 2MB`，JSON 至少按 20MB 正文；超限直接 413。测试：
  `test_oversized_request_rejected_before_body_read`。
- `schemas.py` 给标识符/正文/列表加上资源上界：`doc_ids`/`chunk_ids`/批量删除
  最多 500 项、批量文本最多 64 条、批量编辑最多 200 条、`/embed` 最多 1000 条、
  单个 ID ≤128 字符、单块文本 ≤100k 字符、单篇文本 ≤20MB、问答 q ≤2000 字符。
  `ModelsTestReq.kind` 收紧为 `Literal`，拼错不再静默“什么都没测”。

### 1.6 未鉴权监听告警（低）

`build_app()` 在“无 token 且零密钥”且 host 非回环时输出 warning
（`rag/server.py`）。零摩擦单机体验保留，但部署到 `0.0.0.0` 时不再无提示。

## 2. 数据一致性

### 2.1 `stored_file()` 读错引擎（高）

`stored_file()` 原实现直接 `scalar_rows(store.documents, …)`——那是 LanceDB
旧表。默认 `storage.meta_engine=auto` 时 documents 真源在 SQLite，新上传文档的
`stored_file` 在旧表里是空的，于是：

- 单篇删除漏删归档文件（磁盘泄漏）；
- 重解析误报“没有留档原文”。

修复为走唯一读入口 `docs_query`（`rag/storage/repos/documents.py:139`）。
测试：`test_single_delete_finds_archived_file_in_the_truth_engine`。

### 2.2 删除顺序（高）

`delete_document` / `delete_documents` 原来先 `delete_blob`、再删分块/文档行。
删除中途失败或被 kill 会留下“文档可见、原文已没”的状态，重解析也救不回来
（没有原文）。现在：

1. 持写锁读取归档名、删分块、删文档行；
2. 释放后清理归档；归档删除失败记 **warning**（默认日志可见），留下可回收的
   孤立文件而不是用户数据丢失。

测试：`test_delete_removes_metadata_before_archive`（在 `delete_blob` 被调用的
瞬间断言文档行已不存在）。

### 2.3 删除知识库的级联（中）

`delete_kb` 原来逐篇 `delete_document`：N 次写锁、N 次 SQLite 点查，而且
“列文档”发生在锁外；并发入库可以在列完之后把新文档写进即将删除的库。
现在整个级联（列文档 → 批量删文档 → 删独立分块 → 删库行）在一个写锁内，
文档走批量删除；`delete_documents` 复用同一套“先删元数据、后删归档”的顺序。

另外在入库 pipeline 的最终写锁里校验目标 `kb_id` 仍存在
（`rag/ingest/pipeline.py`），并发的“删除库 + 入库”不会再写出指向空库的文档。

## 3. 并发、异步与性能

### 3.1 `PUT /models` 阻塞事件循环（高）

`registry.reload()` 会重建模型客户端（HuggingFace 可能加载本地模型），
`save_config()` 还要 fsync；两者原来直接跑在协程里。现在：

- `_apply_models_update()` 放入 `asyncio.to_thread`；
- 用模块级 `RLock` 串行化“合并配置 → 重建客户端 → 落盘”，避免两个并发 PUT
  让 registry 用一半旧一半新的配置重建；
- `models/test?persist=true` 的落盘也下沉线程。

### 3.2 健康/统计缓存无并发合流（高）

`/health` 与 `/stats` 的注释明确写着“结果缓存 + 并发合流”，实现却是
`get → compute → set`：冷缓存下 32 个并发请求会做 32 次全表扫描/目录遍历。
`TTLCache` 新增 `get_or_load()`：per-key 单飞锁，等待者复用第一条结果，
不同 key 互不阻塞；loader 抛错时不会缓存“健康”。

`/health`、`/stats` 改为在线程池里调用单飞加载（对账本身是同步 IO），
`age_ms` 仍由缓存如实给出。测试：`tests/test_core_cache.py`（8 并发只算 1 次、
不同 key 不互相阻塞、命中年龄）。

### 3.3 Embedding 查询路径 cache stampede（中）

此前审计把“in-flight 合并”标记为“日后要做”，因为收益取决于真实流量重复度。
本轮 TTLCache 已有单飞能力，**落地成本降到一行且不引入队列等待窗口**：
`Embedder.embed_one` 改用 `get_or_load`。同一个模型的同一段文本在并发下
只打一次 provider（16 并发 → 1 次），等待者拿同一结果。

测试 `test_embed_one_merges_inflight_identical_queries` 从“故意断言会重复调用”
改为“必须只调用一次”；ARCH-AUDIT §4.2 与 PERF 决策文档已同步这一决定变更。

### 3.4 文档详情携带未使用的分块索引（中）

`GET /api/documents/{id}` 默认仍返回 `chunks`（每块含正文）。前端 DocView/Search
都另取分块页，这份数据完全没用，却会让大文档的详情响应成倍膨胀。
新增 `?include_chunks=false`，前端两处使用；默认 true 保持既有契约。
测试：`test_document_detail_can_omit_chunk_index`。

### 3.5 模型 client 的 timeout 配置未生效（中）

`EmbedConfig.timeout` / `LLMConfig.timeout` 只存在于 config.toml，构造
LangChain 客户端时没有传：

- OpenAIEmbeddings：`request_timeout=cfg.timeout`、`max_retries=0`
  （重试只保留 `Embedder` 一层，避免 3×3 放大）；
- ChatOpenAI：`request_timeout=cfg.timeout`；
- Ollama 两类：`client_kwargs={"timeout": cfg.timeout}`。

测试：`tests/test_model_clients.py` 直接断言客户端字段。

## 4. 前端竞态与健壮性

### 4.1 检索请求无取消/序号（高）

URL 变化即检索，但 `run()` 没有 AbortController/序号。快速改参数、后退、
两次检索先后返回时，旧响应可以覆盖新响应——屏幕上的参数与结果集再次脱节。
修复（`web/src/views/Search.tsx`）：请求序号 + AbortController，effect 清理时
abort 上一发；abort 的请求不写 error/busy。

### 4.2 原文检视/设置页旧响应（低）

- `DocPeek` 切换命中时，旧文档请求可能晚到覆盖新命中；现在 useEffect 返回
  abort，并忽略 abort 后的错误；
- `KbSettings`、`Settings` 的模型/健康、`DataPanel`、`KeysPanel`、`KbList`
  加载都加了请求序号，旧响应不再覆盖新状态。

### 4.3 SSE 无终态时静默结束（中）

`streamPost` 只在收到 `done`/`error` 时结束 running；连接被网络/代理截断时，
浏览器仍会正常 `reader.done`，前端把半截答案当完整答案，或 loading 永不结束。
现在跟踪 `terminal`：没有终态且非用户主动停止时调用
`onError("连接已中断，回答可能不完整")`。同时兼容 CRLF、flush decoder。

## 6. 残留风险（本轮未改，需按部署形态判断）

1. **限流是进程内令牌桶**。默认 `api_processes=auto`（最多 4 进程）下，
   配置的每分钟额度实际会乘以进程数。实现跨进程限流需要把桶放进 SQLite，
   会给每个写请求增加一次事务；默认限流关闭，故本轮未做。多进程要严格限流时
   请先固定 `--processes 1`，或接受 N 倍额度。
2. **幂等键是进程内存储**，跨 worker 不共享；同一键的**并发**重试也不会等待
   第一条（数据层仍有内容哈希兜底，不会产生第二份文档，但会重复做一次解析/
   向量化）。单机单进程形态下符合预期。
3. **鉴权/健康缓存是每进程一份**，多 worker 下吊销最长 5s/10s 才在所有进程生效
   （写操作会主动失效本进程）。设计文档已有此边界。
4. **SSRF 没有做完整 DNS pinning**；重定向逐跳校验 + 实际对端 IP 复查已覆盖
   主要攻击面，但连接建立到读取之间的极窄窗口仍在。
5. **CSP 必须允许 `style-src 'unsafe-inline'`**：MUI/Emotion 运行时注入 `<style>`。
   script 侧已收紧到 `'self'`。
6. **没有自动化浏览器 E2E**；前端行为由静态守卫 + 浏览器手工冒烟覆盖。
   `Search` 的取消、SSE 截断等竞态只能靠代码级守卫和单测，无法在 pytest 里
   复现真实网络时序。
7. `RetrieveConfig.query_rewrite` 是**死配置**：配置/响应里有字段，代码里没有任何
   实现。要么下一轮实现查询改写，要么删除该字段（会改 `/api/models` 响应契约）。

## 8. 下一步优化任务（由 §6 残留风险拆解）

优先级按“数据/权限正确性 > 可观测的稳定性 > 合规纵深 > 工程效率”排序。
任务 ID 对应会话任务列表；共享状态基础是 14/15/16 的前置。

| ID | 优先级 | 任务 | 依赖 | 核心验收 |
|---|---|---|---|---|
| 13 | P0 | 跨进程共享状态基础（MetaStore 表 + 迁移 + 失效代际） | — | 两个独立连接共享状态；迁移幂等；无 MetaStore 时降级可见 |
| 14 | P0 | 限流改为共享令牌桶 | 13 | 多进程共享额度；429/Retry-After；不阻塞事件循环 |
| 15 | P0 | 幂等键持久化 + 同键并发合流 | 13 | 跨 worker 同键只执行一次；并发等待；失败可重试 |
| 16 | P1 | 鉴权/健康快照跨进程失效 | 13 | 吊销跨进程立即生效；写后 health 不返回旧快照 |
| 17 | P1 | SSRF 完整 DNS pinning | — | 解析变化后不能连私网；HTTPS 正常；重定向测试全绿 |
| 18 | P1 | Playwright 浏览器 E2E | — | 一条命令、无外网、覆盖深链/检索/API 文档/CSP |
| 19 | P2 | 移除 CSP `style-src 'unsafe-inline'` | — | MUI 正常渲染且无 CSP 违规（或记录不可行原因） |
| 20 | P2 | 处置 `query_rewrite` 死配置 | — | 实现或删除并同步契约；新增“配置必须有读取点”守卫 |
| 21 | P2 | chunked 请求体硬上限 | — | chunked 超限 413、不读完正文、无临时文件残留 |

**建议执行顺序**：13 → 14/15（可并行）→ 16 → 17 → 18 → 20 → 21 → 19。
理由：13 决定 14/15/16 的表结构与降级语义；17 与 18 相互独立，可与 13 并行；
20/21 是小而确定的收口；19 需要单独的技术选型，放在最后避免迁移噪声。

**暂不建议做的**：队列式 embedding 合批。已有 in-flight 合并没有引入等待窗口；
队列式合批会付 10–20ms 等待并扩大失败半径，而真实流量的重复度仍无数据支撑
（见 §3.3 与 ARCH-AUDIT §4.2）。

## 10. 产品逻辑审计与修复（2026-10-21）

这一轮不再看“代码是否优雅”，而是逐条核对**界面在说什么**与**后端实际做什么**。
共确认并修复 11 处语义/交互问题，基线 **625 passed + 6 E2E**。

| 任务分页 offset 被忽略 | 第 2 页与第 1 页完全相同 | `/api/jobs` 增加 offset 并下推到 SQLite/Lance |

**方法上的收获**：
- 这类 bug 单独看每一层都“没错”：API 能返回、UI 能渲染、测试也绿；
  错的是两层之间的口径。以后新功能验收必须同时看「这个数字/开关在说什么」
  与「它来自哪一次查询/哪一个真源」。
- 又抓到一个测试固化错误行为：`test_stream_handles_empty_retrieval` 原先断言
  空结果 delta 在前，而事件契约是 sources → delta → done。测试写成什么样，
  错误就会以“正确”的名义活多久。
