# Raggi 前后端深度审计报告

> 日期：2026-10-02 ｜ 范围：`rag/`（后端 ~2.3k 行）与 `web/src/`（前端 ~1.8k 行）全量审查
> 方法：静态审查 + 隔离环境运行时复现（桩 embedding 服务 + 临时数据目录 + 浏览器实测 UI 全流程）。
> 未触碰运行中的数据实例（其服务在 8000 端口，数据目录 `data/`）。

## 结论概览

现有基线全绿：`pytest` 56 项通过、`tsc --noEmit` 零错误、浏览器全流程无 console 错误。
本报告中的问题**全部位于现有测试未覆盖的运行时路径**，其中 4 个可造成数据丢失/静默失效，建议优先修复。

## A 级：数据 / 一致性破坏

### A1 重解析 / 重切分失败 = 文档分块被清空，文档仍显示 ready

**现象**：对已有文档执行「重新切分」（或重解析）时，若 embedding 服务暂时不可用，请求返回 503，但文档的**旧分块已被删除**：内容从检索中消失，文档列表仍显示 `ready` 和原块数，无任何不一致提示。

**根因**：`rag/ingest/pipeline.py:180-183` —— 显式 doc 路径在流水线**阶段 1 就先删旧分块**，而向量化在阶段 2（锁外）才执行；失败路径（`ingest_file`/`resplit_doc`/`reparse_doc` 的 except，如 pipeline.py:331-333）只把 job 标记 failed，不回滚分块，也不更新 `documents.status`。

**复现证据**（隔离实例，embedding 服务停机后调用 resplit）：
```
POST /api/documents/{id}/resplit  →  503 "embedding 服务不可用（已重试 3 次）"
GET  /api/documents/{id}          →  status: ready | stated chunk_count: 1 | actual chunks: 0
GET  /api/health                  →  status: degraded, count_mismatch: [...]
```

**影响**：用户环境（Ollama 未启动）下点击「重新切分/重解析」即触发。虽然重试成功可从 `documents.text` 重建，但期间文档静默不可检索、状态失真。
**建议**：调整为「先向量化、后删旧写新」；或在失败时恢复旧分块；失败时至少把 `documents.status` 置 `failed` 并保留旧数据。

### A2 删除知识库不清理「独立分块」：残留且仍可被检索

**现象**：知识库下除文档分块外，还可能存在 `doc_id=""` 的「独立分块」。删除知识库后这些分块**不会被删除**，仍挂在已删除的 kb_id 下，且能被检索命中。

**根因**：`rag/store/kbs.py:135-154` `delete_kb` 只级联删除 documents 表里属于该库的文档（进而删其 chunks），未处理 `chunks.kb_id = X AND doc_id = ''` 的独立分块。

**复现证据**：
```
DELETE /api/kbs/{id}                    →  {"ok": true}
GET    /api/chunks?kb_id={已删id}       →  仍返回独立分块
POST   /api/search {kb_id: 已删id}      →  仍能命中该分块
```
前端删除确认文案（`web/src/kbs.ts:136-142`，「将同时删除…全部…分块」）与实际行为不符。

**建议**：`delete_kb` 中追加 `chunks.delete(where="kb_id = '...'")` 的最后一步（文档分块已先删，剩余即独立分块）。

### A3 删除分块不回写 `documents.chunk_count`：计数永久漂移

**现象**：从文档中删除任意分块后，`documents.chunk_count` 保持旧值，`/api/health` 永久显示 `degraded`、`count_mismatch`；文档列表/知识库卡片块数虚高。

**根因**：`rag/chunk_edit.py:228-230` `remove_chunk` 仅删除行，未调用 `touch_doc_count`（对比：编辑 `edit_chunk`、新增 `add_manual_chunk`、重切分都会回写）。

**复现证据**：
```
DELETE /api/chunks/{id}  →  {"ok": true}
GET    /api/health       →  status: degraded, count_mismatch: [{stated: 1, actual: 0}]
（UI 健康页同步显示「计数不一致 1 个文档」）
```

**影响**：无修复入口——用户只能靠重切分/重新入库“意外”修复；degraded 长期存在会让健康检查失去信号价值。
**建议**：`remove_chunk` 内取到分块的 `doc_id` 后调用 `touch_doc_count`；另建议提供 `/api/reconcile`（或健康页一键对账）批量修复计数。

### A4 模型设置「保存并热切换」不落盘；落盘与读取路径不一致

**两层问题**：
1. **前端不落盘**：`web/src/system.ts:161-179` 的保存调用 `PUT /api/models` **不带 `?persist=true`**，后端（`rag/api/models.py:30-33`）persist 默认 `False`，仅热切换内存。UI 提示「配置已保存并热切换」，实际重启即丢。DESIGN §10 约定「PUT 落盘 config.toml」。
2. **落盘路径 ≠ 启动读取路径**：`save_config`（`rag/config.py:132-155`）写入 `settings.data_dir/config.toml`；而启动读取的 `toml_file` 固定为 cwd 相对路径 `"data/config.toml"`（`rag/config.py:72`）。使用 `--data /srv/xxx` 时，即使落盘到 `/srv/xxx/config.toml`，重启也会去读 `./data/config.toml`（不存在），配置静默失效。

**复现证据**：
```
PUT /api/models（无 persist）        → 响应 persisted: false
重启实例后 GET /api/models           → 配置回退
PUT ?persist=true                    → 文件写到 /tmp/.../data/config.toml
ls /home/admin/Raggi/data/config.toml → No such file（读取的是另一路径）
```

**建议**：① 前端带 `?persist=true`（或后端将 PUT 默认改为落盘）；② 把 TOML 读取路径改为「`--data` 解析后的 data_dir/config.toml」，需调整 `settings_customise_sources` 的构造时机。

## B 级：功能错误 / 明显缺陷

### B1 过滤条件命中 0 文档时检索 503（`doc_id IN ()`）

`rag/retrieve.py:61-72` 的 `_doc_ids_by_attr` 在无匹配文档时返回 `[]`（而非 None），`_in_clause`（:56-58）生成非法的 `doc_id IN ()` → LanceDB SQL 解析错误 → 503。

**复现**：
```
POST /api/search {"q":"逆变器","filters":{"mime":"application/x-nonexistent"}}
→ 503 "Error parsing statement: ... WHERE enabled = true AND doc_id IN ()"
```
**修复**：`ids == []` 时改为恒假条件（如 `doc_id IN ('__none__')`）或直接短路返回 0 结果。parser_engine 过滤同样受影响。

### B2 错误提示误导：一切都归因「embedding 服务不可用？」

`rag/api/search.py:31-34`、`documents.py:67-69/89-91/127-129` 等把所有 `Exception` 一律包装为「…（embedding 服务不可用？）」的 503。实测中，**SQL 语法错误、Arrow 维度失配**都被伪装成模型服务故障，直接把排障带偏。
**修复**：仅对 `EmbedUnavailable` 做 503 特判（已有全局 handler），其余异常保留原始信息（500 + 原生错误摘要）。

### B3 修改 `embed.dim` 后写入全挂；警告为死代码；reindex 无法修复

- `rag/models/registry.py:37-51`：`reload()` 中 `old.embed_cfg` 与 `self.settings.embed` 是**同一个对象**（`_build` 里 `embed_cfg=s.embed`，而 `merge_sub` 就地修改该对象），比较恒相等 → **warnings 永远为空**。实测 dim 16→32 后 `warnings: []`。
- 维度失配后，所有入库/编辑持续失败（实测：`Arrow error: ... Variable column 'vector' has variable length vectors`），且错误又被包装成「embedding 服务不可用？」（见 B2）。
- 设置页把 dim 做成普通可编辑输入（`web/src/system.ts:27`），提示「改动后需重建索引」；但 `POST /api/reindex`（`rag/store/lancedb.py:207-220`）只重建索引、不改表 schema —— 实测 **reindex 后写入仍失败**，唯一出路是把 dim 改回去。

**建议**：① 修复 reload 警告（deepcopy 旧配置或保存旧值快照）；② dim 输入改为危险操作（二次确认 + 明确「会导致写入失效，必须回退或迁移数据」）；③ 修正提示语，说明 reindex 无法修复维度变更。

### B4 URL 入库不做正文抽取：原始 HTML 入索引

`rag/parsing/loaders.py:69-74` `load_url` 把 urllib 抓到的**原始 HTML 原样**作为正文（含 `<script>`、`<style>`、导航栏），title 直接用 URL。DESIGN §10 承诺「网页正文抽取」。
**复现**：入库本地 HTML 页后，`documents.text` 原样保留 `<!DOCTYPE html>…<script>var secret=…`。
**修复**：html→text 提取（BeautifulSoup / readability / unstructured 任一），至少剥 script/style/标签并取 `<title>`。

### B5 前端丢弃保存响应的 warnings

`web/src/system.ts:161-179` `saveModels` 不读取响应体，`warnings` 字段被完全忽略（后端即使产生警告用户也看不到；当前因 B3 该字段恒空）。
**修复**：解析响应并 toast/banner 展示。

## C 级：体验 / 边界 / 一致性

- **C1 报告导出 UI 缺失**：后端 `POST /api/search/report`（`rag/api/search.py:73-83`，Markdown 导出）已实现，但 `web/src` 全库无调用——DESIGN §0 四大核心交付之一「前端查看与报告」的“报告”没有入口。建议检索页加「导出报告」按钮。
- **C2 列表硬截断**：文档列表 `limit=200`（`web/src/docs.ts:86/100`）、分块列表 `limit=500`（`web/src/chunks.ts:88`）且无分页提示；`/api/chunks` 无 `total`、无稳定排序。`web/src/kbchunks.ts:74-76` 先取该库**前 500 条全部分块**再过滤 `doc_id=""`——文档分块越多，独立分块越可能整个不可见。建议后端支持 `doc_id=''` 过滤参数与分页。
- **C3 Rerank 卡片无效字段**：`web/src/system.ts:35-42` 的 rerank 卡片包含 `base_url`/`api_key`，而后端 `RerankConfig`（`rag/config.py:23-29`）没有这两个字段，`merge_sub`（`rag/api/_common.py:29-38`）静默忽略。用户会以为配置了 rerank API 端点。
- **C4 `created_at` 被覆盖**：`rag/ingest/pipeline.py:243-249` 重切分/重解析时 `upsert_documents` 重新写入 `created_at=_now()`（merge_insert 全列更新）。实测 resplit 前后 `created_at` 由 `18:47:00` 变为 `00:16:15`，「入库时间」列失真。修复：显式保留旧行 created_at。
- **C5 统计条丢格**：`web/src/docs.ts:433-446` `refreshKb` 重建 `#kbStats` 时不含「分块方案」格（`openKb` 有），入库后该格消失。
- **C6 N+1 请求**：`web/src/docs.ts:114-116` 对每个文档单独请求 `/plan`（Promise.all）。200 文档 = 200 请求。建议列表接口带方案摘要。
- **C7 停用/启用无写锁**：`rag/chunk_edit.py:213-225` `set_chunk_enabled` 未包 `store.write_lock()`（其余写路径均包），与并发入库存在理论竞态。

## 环境观察（与问题排查相关的现状）

- 8000 端口运行中的实例：**Ollama（11434）未启动**，检索/入库即时失败（错误提示文案本身尚可）；当前数据为空（0 文档、1 个知识库、8 条 jobs、69 个表版本），`data/config.toml` 不存在——即任何在设置页做的修改都不会留下痕迹（A4）。
- 本报告所有破坏性验证均在隔离数据目录 + 桩 embedding 服务上进行，已清理，未触碰 `data/`。

## 已排查、确认无问题的项（避免误报）

- `search()` 全表扫描无行数上限（`_doc_chunks`/`_contexts`/`_titles` 实测 50/50 全量返回）。
- FTS 索引对已删除行即刻不可见（删除后检索不到）。
- 前端 wiring（DOM id、具名导出、产物新鲜度）与既有测试覆盖良好；浏览器实测全流程无 console 错误、无失败请求。
- `pytest` 56 项、`tsc` 均通过——本报告的 A/B 级问题均未被现有测试覆盖，建议每条修复后补对应回归测试。

## 修复优先级建议

1. **A1**（数据安全：先向量化后清旧 + 失败置 failed）
2. **A3 + A2**（对账回写 + 级联完整性，可一并补 `/api/reconcile`）
3. **A4**（persist 两处修复，否则一切设置类操作都不可信）
4. **B1 + B2**（检索正确性 + 错误分类，收益大成本低）
5. **B3**（维度保护，避免设置页瘫痪系统）
6. 其余按 C 级逐步处理
